- Layer types: source {video, anim_img, none}, source-multi (several anim_img at once, Transform.multiTrack), transform {chromakey, alphamask, reframe, http, none}. docs/spec_formats.md is outdated (no alphamask/reframe/source-multi).
- Source layers draw straight onto the GPU canvas (video: canvas.pixelsYUV / surface).
- chromakey + alphamask: child.renderPix -> GPU->CPU readback (popSurface S_MODE_PIXELS, or yuvToRGBA on CPU) -> CPU per-pixel op (ImageTransform) -> canvas.pixels upload. Cost ∝ child display area, CPU-bound even on the gpu tier -> tier factor not uniform for transforms.
- reframe: render-to-surface (push/popSurface), GPU only.
- Transform children: 1 = layer directly below; 0 = ALL layers below (in engine, unused by every current show). chromakey/alphamask loop over children and keep only the last node's pixels (code reading, untested).
- Transform:renderPix returns null for chromakey/alphamask/reframe/multiTrack -> stacking a transform on a transform not supported.
- display: full | window_relative | window_absolute; decode res (source) independent of display area.
- Current coverage: chroma only full-screen forecast presenter; alpha only forest (132x86 .. full); reframe only f1 portrait; children=0 never; http never.
- Tools for new assets: obm/tools AnimateAF/SegmentAF (.af), SegmentAM (.mask), SegmentH264 (Dana); ffmpeg libx264 for video (Constrained Baseline, L3.1, yuv420p, no B, refs 1, 25 fps, 10 s segments).
- Engine gotchas (2026-10-30): request "N" after orientation = number of layer-graph root nodes; video assets must be H2i (5-byte int4 length + byte type before each NAL); site renders black frames with exit 0 on undecodable input; chromakey on a scaled windowed child breaks the frame (draws at 0,0).

- Size sweep (c1, LRU sim): a0.5 / a1.2 hit at 50 MiB .13-.17/.05-.08, 100 .22-.25/.13-.17, 200 .32-.35/.25-.28, 400 .37-.40/.36-.37 -> converge once the cache holds the window's working set; a1.2 never beats a0.5.
- Why not real-world Zipf intuition: only 6 shows, ~45 viewers in 600 s, catalogue (kinds x segments) >> requests -> compulsory misses dominate; skew over 6 shows shifts WHICH show is hot, not how many repeats. Real-world skew gain needs catalogue >> cache and many concurrent viewers.

## SEGMENT CACHE LRU vs LFU SIM (11-06, temp/seg_lfu_sim/sim.py -> result.csv; same event replay as bin_why; LFU = Rust PolicyCache rank (uses while cached, last_use))
- Hit ratio mean over 8 seqs: single 100 MiB lru .194 -> lfu .237 (+4.3 pts, better on 8/8); bins 50+50 lru .190 -> lfu .231 (8/8). 50 MiB .110 -> .156; 200 MiB .296 -> .309 (gap closes as cache holds working set).
- Saved service demand (sum none-run asset+work+net of hits): lru100 468 s -> lfu100 578 s (+23%); bin lru 461 -> bin lfu 556.
- Gain biggest at a1.2 (fixes the eviction problem above): 2042 a1.2 c1 .130 -> .206, c2 .148 -> .223; 2037 a1.2 c1 .170 -> .193; a0.5 +2-5 pts. Why: 60% of requests are first-time / one-hit paths; LRU lets them flush items that already got a hit, LFU keeps uses>=2 items.
- Bins add nothing on top of LFU (bin lfu .231 ~ lfu100 .237) -> no need to code LFU bins (bins are LRU-only in Rust). Rec: run S with OBM_SEGMENT_CACHE_POLICY=lfu, 100 MiB, 8 seqs (env only, no code change).
- Caveats: latency feedback not modelled (hits shorten queue -> earlier adds); 600 s window so LFU staleness never shows; sim lru100 matched real S within .01-.02.

## COALESCING POTENTIAL (11-06, inline calc on mct_none_1, 8 seqs)
