# Synthetic OBM Shows (round 1)

Shows built from generated videos, used to test the offload cost model on **content and layer
structures the six BBC shows do not contain**. The prediction should work from generic metadata
(layer types, resolutions, areas, bitrates), not from show identity. These shows check that.

## Layout

Same layout as `obm/`, so the files can be served by the main server or any web server:

```
syn_video/
  build.py                  generates everything below (ffmpeg + JSON)
  request_kind_syn.txt      every valid request path, segment as t_start/t_end
  assets/syn/meta/*.json    one spec per video (seg_base, w, h, frames) + key_chroma.json
  assets/syn/video/*.h264   10 s segments (gitignored, rebuilt by build.py)
  shows/<show>.json         show specs; shows/<show>.png thumbnails (gitignored)
  docs.md                   this file
```

To build: `syn_video/build.py` (about 1 min on om: one ffmpeg per video in parallel; existing
videos are skipped, `--force` re-encodes them). Needs ffmpeg and Dana (`dana`, `dnc`) on the host:
the segments are written by OBM's own `obm/tools/SegmentH264.dn`, compiled on first use.

To use in the cluster, copy into `obm/`: `cp -r syn_video/assets/syn obm/assets/ && cp syn_video/shows/syn_* obm/shows/`.
Sites fetch everything from the main server, so only om needs the files.

## How the videos are made

Every video is generated by an ffmpeg `lavfi` source, so content is fully controlled and has no
licence issues. The encoding matches the existing OBM assets exactly:

| Property | Value | Same as existing assets |
|---|---|---|
| Codec | H.264, `libx264` | yes |
| Container | OBM's **H2i** framing: every NAL (Annex B, with start code) is preceded by a 5-byte header, int4 length + byte frame type, so the player finds frames without scanning. Written by `obm/tools/SegmentH264` from a full Annex B stream (x264's leading SEI NAL removed first: the tool needs the stream to start with an SPS) | yes |
| Profile / level | Constrained Baseline, 3.1 (720p and below), 4.0 (1080p) | yes |
| Pixels | yuv420p, no B-frames, 1 reference frame, 25 fps | yes |
| Segments | 10 s = 250 frames, each starts with IDR + SPS/PPS (`repeat-headers`) | yes (existing ones cut at keyframes) |
| GOP | fixed 250 frames, no scene-cut keyframes | existing: scene-cut keyframes too |
| Length | 30 s (3 segments) | shorter than the BBC shows |
| Bitrate | fixed (CBR-like, `maxrate = b:v`), 2 Mbit/s at 720p | about the same as `spiders720p` (~2 Mbit/s) |

### Content classes

| Content | ffmpeg source | Character |
|---|---|---|
| `calm` | `gradients`, slowly drifting colours | almost no detail or motion: easiest to encode |
| `graphics` | `testsrc2` | sharp edges, moving pattern and counter: medium |
| `texture` | `mandelbrot`, zooming over the 30 s (`end_pts` = 750 *frames*, `maxiter` 600) | constant motion; detail grows over the clip: segment 0 shows the whole set, segments 1–2 dense boundary detail |
| `noise` | grey + temporal noise | every block changes every frame: worst case for the encoder |
| `keyfg` | key-colour background (36, 73, 111), moving `testsrc2` box in front (also at 640x360 and 320x180 for `syn_chroma_area`) | chroma-key foreground, like the forecast presenter |

Variants of `texture`: source bitrate 1 / 2 / 6 Mbit/s (`texture_br1`, `texture`, `texture_br6`),
and decoded resolution 480p / 720p / 1080p (`texture_480`, `texture`, `texture_1080`). Grid tiles:
640x360 and 426x240 versions of the contents.

## How OBM layers cost (why these classes)

From the engine source (`obm/Experience.dn`, `Transform.*.dn`, `Track.video.dn`):

- **Source layers** (`video`, `anim_img`) are drawn straight onto the GPU canvas. Stacking them is
  cheap; each video adds a decode.
- **Pixel transforms** (`chromakey`, `alphamask`) pull their child layer's pixels back from GPU to CPU
  (`renderPix`), process every pixel on the CPU, and upload the result (`canvas.pixels`). Their cost
  grows with the **display area of the child**, and it is CPU work even on the gpu tier.
- **`reframe`** renders into an off-screen GPU surface: cheap.
- A transform applies to the layer directly below (`children: 1`) or to all layers below (`children: 0`).
- **Decoded size and displayed size are separate**: a 1080p video in a small window is a full 1080p
  decode but a small draw.
- **Encode** (GPU readback of the whole frame, RGB to YUV, x264) works on the final composite, so its
  cost depends on how much of the *visible* picture moves and how detailed it is, not on the layer count.

Two engine details that matter when writing shows and requests (found while testing):

- **The number after the orientation in a request is the number of root nodes** of the layer graph, not
  the number of layers (`OffloadSite_new.dn` passes it to `Experience.loadVariant` as `renderLayers`).
  A source layer adds a root, a `children: 1` transform replaces the last root, a `children: 0`
  transform merges all roots into one. E.g. forecast: 5 layers, 4 roots. `build.py` computes it
  (`root_nodes`); a wrong count crashes the site (`array index out of bounds`, Experience.dn).
- **Chroma on a scaled (windowed) layer is broken**: `Transform.chromakey` draws its output at (0, 0),
  and a child whose video size differs from its window is drawn through a push/pop surface that
  leaves the rest of the frame white. The BBC shows only key full-screen layers. `syn_chroma_area`
  therefore uses keyed videos made at their window size, with windows at the top-left.

## Shows and what each one tests

| Show | Variants × combinations | Class | Holds fixed | Varies | Expected effect |
|---|---|---|---|---|---|
| `syn_content` | 1 × 6 | content complexity | one full-screen 720p video, no transforms | content (calm, graphics, texture, noise) and source bitrate (1/2/6 Mbit/s) | decode: rises with bitrate, little with content. Render: same for all. **Encode: calm << graphics < texture < noise**, the main signal |
| `syn_combo` | 1 × 9 | one show, very different combinations | layout | background (calm / texture / noise), full-screen chroma foreground (off / on, keyed or not) | cheap (calm) vs heavy encode (noise) vs heavy CPU chroma (keyfg + chroma). A per-show average or lookup cannot predict this; a feature model should. `keyfg` without chroma fully covers the background (occlusion: background decoded, invisible to encode) |
| `syn_chroma_area` | 3 × 2 | transform area | same keyed content, unscaled | keyed layer 320x180, 640x360, 1280x720 (25 / 50 / 100 % of the width), chroma off / on | chroma cost ∝ keyed area (~1 : 4 : 16 for the per-pixel part). The gpu tier should gain less from the GPU when chroma is on (CPU readback) |
| `syn_res` | 4 × 1 | decoded vs displayed size | Mandelbrot content | 480p / 720p / 1080p full screen; 1080p in a 320x180 window | decode ∝ decoded pixels (1080p ≈ 2.25× 720p); render ∝ displayed area; the small-window 1080p keeps the decode cost but adds little render cost |
| `syn_grid` | 2 × 1 | number of video streams | no transforms, whole screen covered | 4 tiles (640x360) vs 9 tiles (426x240) | decode grows with the stream count (per-stream overhead) even though total pixels are similar; render ~ the same |

27 request kinds in total (`request_kind_syn.txt`); combinations that apply chroma to an `off`
foreground are left out (nothing to key).

## How they were tested

`temp/syn_test/test_render.py` (gitignored) runs each request kind through the real offload site on
the host, without Docker:

1. a local web server on `:8080` serves `obm/` and `syn_video/` assets and shows (the site's `ASSET_HOST`);
2. `dana OffloadSite_new -req <path> -out <file> -raw` renders one segment (direct mode, plain H.264);
3. the output is checked with `ffprobe` (codec, size, 250 frames), a full `ffmpeg` decode (no errors),
   **picture content** (luma range > 16 in the frames at 1 / 5 / 9 s), and a contact sheet of those
   frames that was also inspected by eye;
4. `ffplay -autoexit temp/syn_test/out/<file>.h264` to watch one.

The content check matters: when the site cannot decode an input (e.g. plain Annex B instead of H2i)
it still encodes 250 frames, all black, with exit code 0 and a clean decode.

**Result (2026-10-30):** all 27 request kinds pass on segment 0 and segment 2 (the last segment, so
later segments decode on their own).

Results are in `temp/syn_test/out/results_s0.csv` / `results_s2.csv` with the site's stage timings.
These are single runs on the host (om, host GPU composition, CPU decode), to check the shows work and
see the order of magnitude; the cluster calibration should use the six sites like `stat_collect.py`.
First observations (segment 0, ms):

| Check | Measured | Reading |
|---|---|---|
| Chroma render cost vs keyed area (`syn_chroma_area`, render on − off) | 25 %: +199, 50 %: +800, 100 %: +2500 | ≈ 1 : 4 : 12.5, close to the 1 : 4 : 16 area ratio: per-pixel CPU cost |
| Decode vs decoded resolution (`syn_res`) | 480p 510, 720p 999, 1080p 1995 | ≈ ∝ decoded pixels (0.44× / 1× / 2.25×) |
| 1080p in a small window (`d1080_small`) | decode 3002 = 1080p (~2000) + calm background (~800) | decode is additive per stream; render stays small (319) |
| Decode vs source bitrate (`syn_content`, texture) | 1 / 2 / 6 Mbit/s: 838 / 1010 / 1351 | rises with bits, less than linearly |
| Stream count (`syn_grid`) | 4 tiles 918, 9 tiles 1057 vs one 720p ~1000 | same total pixels → about the same decode; per-stream overhead is small |
| Encode vs content (`syn_content`) | calm 1439, graphics 1262, texture 1370, noise 1540 | small spread (±10 %): the site encoder's cost depends little on content at this resolution |
| Same show, different combinations (`syn_combo`) | work 2271 (calm) → 5831 (calm + keyed fg + chroma) → 6635 (texture + chroma) | 2.9× spread within one show: a per-show average cannot predict this |
| Occlusion (`syn_combo`, keyfg over texture, chroma off) | decode 1360 (both videos decoded) | the hidden background is still decoded |

## Not in round 1

- `alphamask` and `anim_img` layers (need OBM's own `.mask` / `.af` formats, built with `obm/tools`
  `SegmentAM`, `AnimateAF`, `SegmentAF`).
- Transforms over the whole stack (`children: 0`), which no existing show uses.
- An opaque overlay over a heavy video as its own class (partly covered by `syn_combo`).
- Portrait (`reframe`) versions.
